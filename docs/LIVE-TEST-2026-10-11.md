Read-only checks on the user's connected SanDisk after explicit permission to temporarily connect this computer's Wi-Fi. No firmware, device settings, files, credentials, or device service configuration changed. No login attempts were made. Ethernet remained unchanged. Wi-Fi was restored to its original `Lan` connection after testing.

## Wi-Fi and local services

- Advertised SSID: `SanDisk Media 37CB`; scan reported signal 97 and no advertised security.
- Connection succeeded. Host DHCP address: `192.168.11.100/24`.
- DHCP DNS: `192.168.11.1`; **no DHCP gateway**.
- Three Wi-Fi-bound pings to `192.168.11.1`: 3/3 replies, 0% loss, average 5.934 ms.
- Bounded single-host TCP checks: ports **21 (FTP), 23 (Telnet), 80 (HTTP)** accepted connections; ports **22, 443, 445, 8080** refused connections.
- Telnet returned negotiation bytes; no authentication was attempted.
- HTTP GET `/`, bound to the Wi-Fi source address: **200**, `text/html`, title **SanDisk Wireless Media Drive**. Only an 8 KiB preview was read. A page comment reported web UI version `0.64.1281.0211`; this is not the firmware version.

## Internet/uplink

- The host routing table had no default route through SanDisk; Ethernet remained the default Internet route.
- An HTTPS connection attempt to `1.1.1.1`, explicitly bound to `wlan0` with proxies disabled and a 3-second connection timeout, **timed out**. This deliberately avoided treating Ethernet Internet access as SanDisk success.
- A DNS A query for `example.com`, sent directly to `192.168.11.1:53` from `192.168.11.100`, **timed out** after 4 seconds.

**Result:** live SanDisk Wi-Fi, DHCP address assignment, ICMP reachability, and the web UI work. Internet through the SanDisk was **not demonstrated** and is not currently usable through the supplied DHCP configuration. This does not disprove the firmware's AP/client NAT capability: the phone uplink may be disconnected or sharing disabled. The test did not inspect or change upstream settings.
